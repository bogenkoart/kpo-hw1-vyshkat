# ВышКат — учёт парка кикшеринга

> «Доедем до дедлайна». КПО, домашнее задание №1: SOLID · DI-контейнер · юнит-тесты.

Консольное приложение на **Go**: приём техники через техосмотр, вещи на балансе,
отчёт по числу единиц и суммарной энергии, список транспорта для новичков,
инвентарная ведомость.

## Запуск

Нужен Go 1.22+.

```bash
go mod tidy                  # один раз: скачает DI-контейнер go.uber.org/dig и создаст go.sum
go run ./cmd/vyshkat -demo   # демо-сценарий: все возможности приложения подряд
go run ./cmd/vyshkat         # интерактивное меню
go test ./... -cover         # тесты с покрытием по пакетам
```

Общее покрытие по всему проекту:

```bash
go test -coverpkg=./... -coverprofile=cover.out ./... && go tool cover -func=cover.out | tail -1
# total: ~90%
```

## Что умеет

| Требование из ТЗ | Где в коде |
|---|---|
| 1. Добавление транспорта в парк | `fleet.Fleet.AcceptVehicle`, меню «1» |
| 2. Техосмотр перед приёмкой (принять/отклонить) | `inspection.ServiceCenter.Inspect`, журнал отказов — `Fleet.Rejections`, меню «6» |
| 3. Суммарное суточное потребление энергии | `Fleet.TotalDailyKWh`, `Fleet.Report`, меню «3» |
| 4. Список для новичков (простота ≥ 6) | `fleet.MinSimplicityRule`, `Fleet.BeginnerVehicles`, меню «4» |
| 5. Вещи на балансе и вывод инвентарных номеров вместе с техникой | `Fleet.AddItem`, `Fleet.Inventory`, меню «2» и «5» |
| 6. Демонстрация всех сценариев | `console.App.RunDemo`, флаг `-demo` или меню «7» |

Техосмотр отклоняет транспорт, если износ выше 60 % или у электротранспорта
не указан либо подозрительно большой суточный расход (> 1,5 кВт·ч). Нормативы — в
`inspection.DefaultConfig`.

Инвентарные номера выдаются автоматически при постановке на баланс:
`VK-T-0001…` — транспорт, `VK-I-0001…` — вещи. Отклонённый транспорт номер не получает.

## Структура

```
cmd/vyshkat/          main: создаёт контейнер и запускает приложение
internal/domain/      модель: интерфейсы Inventoried, EnergyConsumer, Vehicle, Item; виды транспорта и вещей
internal/inspection/  ServiceCenter — сервис техосмотра
internal/fleet/       Fleet — учёт парка; объявляет нужные ему абстракции Inspector и BeginnerRule
internal/console/     меню, ввод/вывод, каталог видов для меню, демо-сценарий
internal/di/          composition root: регистрация зависимостей в контейнере dig
```

Зависимости направлены внутрь: `console → fleet → domain ← inspection`.
`fleet` не знает о пакете `inspection`, а связывает их только `di`.

## Модель

```
Inventoried (Name, Kind, InventoryNumber, AssignInventoryNumber)
├── Vehicle (+ Simplicity, WearPercent)
│   ├── Bicycle
│   ├── Scooter           + EnergyConsumer
│   └── EBike             + EnergyConsumer
└── Item
    ├── Helmet
    ├── DockStation       + EnergyConsumer
    └── ChargingCabinet   + EnergyConsumer
```

* **`EnergyConsumer` — отдельный интерфейс**, а не поле в базовом типе: велосипед и шлем
  энергию не потребляют, и у них просто нет метода `DailyEnergyKWh`. Суммарная энергия
  считается проверкой «реализует ли объект `EnergyConsumer`», поэтому учитываются
  и транспорт, и вещи (док-станции, шкафы).
* **Повторное использование кода — через встраивание** (`Asset`, `vehicleBase`, `energy`,
  `item`), так в Go принято вместо наследования.
* **`Item` отдельно от `Vehicle`**: вещь нельзя по ошибке передать в `AcceptVehicle`,
  а транспорт — поставить на баланс в обход техосмотра. Это проверяет компилятор.
* **Инварианты проверяются в конструкторах** (`NewScooter` и др.): простота 1–10,
  износ 0–100 %, непустое имя, неотрицательная энергия. Объект в невалидном состоянии
  создать нельзя. А *допустим ли* исправный, но изношенный самокат в парк, решает уже
  техосмотр, а не конструктор.
* Сотрудники, станции аренды и склад запчастей пока не реализованы (не требуются),
  но модель к ним готова — см. вопрос 3 ниже.

## SOLID — где и зачем

| Принцип | Где применён |
|---|---|
| **S** — единственная ответственность | `ServiceCenter` только решает про техосмотр; `console.App` только ввод/вывод (бизнес-логики в нём нет); `domain` — данные и инварианты; `di` — только сборка. |
| **O** — открытость/закрытость | Новый вид транспорта = новый тип в `domain` + одна строка в `console/catalog.go`. `Fleet`, `ServiceCenter`, отчёты не меняются: они работают с интерфейсами `Vehicle`/`EnergyConsumer`. Правило «для новичков» тоже меняется без правки `Fleet` — передаётся другая `BeginnerRule`. |
| **L** — подстановка Лисков | Любой `Vehicle` обрабатывается `Fleet` и `ServiceCenter` одинаково; ни один вид не ломает контракт (например, не бросает панику на `DailyEnergyKWh`), потому что неэлектрический транспорт этот метод просто не реализует. |
| **I** — разделение интерфейсов | Маленькие интерфейсы: `EnergyConsumer` (1 метод), `fleet.Inspector` (1 метод). Велосипед не обязан реализовывать «пустой» расход энергии. |
| **D** — инверсия зависимостей | `Fleet` зависит от абстракции `fleet.Inspector`, объявленной у потребителя, а не от `*inspection.ServiceCenter`. Конкретную реализацию подставляет DI-контейнер в `internal/di/container.go`; в тестах подставляется заглушка. |

### DI-контейнер

Используется [`go.uber.org/dig`](https://github.com/uber-go/dig) — рантайм-контейнер,
похожий на `Microsoft.Extensions.DependencyInjection` из .NET: зависимости
регистрируются через `Provide` (по типам параметров и результатов конструкторов),
приложение получается через `Invoke`, а `Decorate` позволяет подменить зависимость,
что и используется в тестах. Весь граф собирается в одном месте — `di.NewContainer`.

## Обязательные вопросы

**1. Какой принцип SOLID применён наиболее явно и где?**
Инверсия зависимостей (DIP). `fleet.Fleet` получает техосмотр через интерфейс
`fleet.Inspector` (`internal/fleet/fleet.go`), который объявлен в самом пакете `fleet`.
Пакет `inspection` реализует этот интерфейс, но `fleet` его не импортирует.
Связь «интерфейс → реализация» задаётся в одной строке контейнера
(`internal/di/container.go`), и в тестах эта строка подменяется через `Decorate`.

**2. Какой принцип сознательно ограничен и почему это приемлемо?**
SRP у `fleet.Fleet`: он одновременно хранит данные в памяти, выдаёт инвентарные номера
и строит отчёты. По учебнику стоило бы выделить `Repository`, `NumberGenerator` и
`ReportService` с интерфейсами. Но при трёх самокатах, без БД и без второй реализации
эти интерфейсы были бы «мёртвым» SOLID. Когда появится хранилище (БД), хранение
вынесем за интерфейс `Repository`, и публичный API `Fleet` при этом не изменится.

Второе осознанное упрощение — `Inventoried` объединяет чтение номера и
`AssignInventoryNumber`. Отдельный интерфейс «только для чтения» пока никому не нужен,
а повторно присвоить номер нельзя (`ErrNumberAlreadyIssued`), так что инвариант защищён.

**3. Что сломается (или не сломается) при расширении?**
* *Новый вид транспорта* (например, моноколесо): добавить тип `Monowheel` со встроенными
  `vehicleBase` и `energy` и метод `Kind()`, плюс строку в `console/catalog.go`.
  `Fleet`, `ServiceCenter`, отчёты и тесты не меняются. Ничего не ломается.
* *Сотрудник службы эксплуатации*: новый тип вне `Inventoried`, потому что на баланс его не ставят.
  Он просто не может попасть в `Fleet.Inventory` и в отчёты — компилятор не даст.
  Учёт сотрудников будет отдельным сервисом рядом с `Fleet`. Ничего не ломается.
* *Склад запчастей*: запчасть станет новым `Item` (например, `SparePart` с количеством).
  Если запчасти нужно учитывать отдельно от «вещей в прокате», то тут ограничение
  из вопроса 2 и сработает: придётся выделить хранилище из `Fleet`. Это и будет
  тот самый момент, когда разделение оправдано.
* *Новое правило для новичков* (например, «простота ≥ 6 и износ ≤ 30 %»):
  новая функция `BeginnerRule` в контейнере, а `Fleet` не меняется.

**4. Какой тест фиксирует техосмотр и правило «для новичков»; как подменяется зависимость?**
* `internal/inspection/service_center_test.go` → `TestServiceCenter_Inspect`:
  табличный тест реальных правил техосмотра (граница износа 60 %, расход, несколько причин сразу).
* `internal/fleet/fleet_test.go` → `TestAcceptVehicle_RejectedByInspection_NotAdded`
  и `TestAcceptVehicle_ApprovedByInspection_GetsNumber`: `Fleet` создаётся с
  `fakeInspector` (fake, который возвращает заданное решение и запоминает вызовы).
  Проверяется, что при отказе транспорт не попадает в парк и не получает номер.
* `internal/di/container_test.go` → `TestContainer_InspectorCanBeReplaced`:
  подмена **через DI-контейнер**. `c.Decorate(func(fleet.Inspector) fleet.Inspector { return stub })`
  заменяет `ServiceCenter` на заглушку `rejectAll`. После этого исправный самокат,
  которого реальный техосмотр принял бы, отклоняется.
* `internal/fleet/fleet_test.go` → `TestBeginnerVehicles_ThresholdSix` (простота 5 — нет,
  6 — да, граница включена) и `TestBeginnerVehicles_CustomRuleInjected` (подмена правила).

  подменяет техосмотр в тесте, почему `Fleet` сознательно не разделён на репозиторий
  и сервис отчётов.

## Code style

`gofmt`, `go vet ./...` — без замечаний. Ошибки возвращаются значениями (`error`) и
проверяются через `errors.Is`. Паника допустима только в `must` для заведомо корректных демо-данных.
